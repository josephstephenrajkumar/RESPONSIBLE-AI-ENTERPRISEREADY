# Design Record — Real Ragas + TruLens Integration

Date: 2026-09-07

```text
Goal:
  Replace the ragas_eval.py and trulens_eval.py scaffolding with real,
  library-backed evaluators judged by the existing Groq model, and surface the
  results in a new frontend evaluation dashboard.

Current behavior:
  - ragas_eval.evaluate_fairness(answer): synchronous regex/keyword matcher against
    a hardcoded biased-term list. No LLM call, no `ragas` import.
  - trulens_eval.evaluate_explainability(answer): synchronous function returning a
    hardcoded dict (`explanation_level: 'high-level'`). No `trulens` import.
  - main.py's /chat framework-mode branch calls both synchronously
    (`framework_fairness(answer)`, `framework_explainability(answer)`) at
    backend/app/main.py:294-297.
  - Results are stored verbatim in ResponsibleAIResponse.fairness/.explainability
    (untyped dict fields, schemas.py) and persisted into audit_events.responsible_ai
    via append_audit_event (database.py:309). No aggregate report exists for them.
  - Frontend shows these only as ad hoc inline fields in MessageBubble.jsx; no
    dashboard, no GET /reports/evaluations endpoint exists.

Proposed behavior:
  - ragas_eval.evaluate_fairness(answer) becomes `async def`. It builds a
    single-row Ragas dataset (`user_input`/`response`) and runs
    `ragas.metrics.AspectCritic` with a bias/fairness rubric through
    `ragas.evaluate()`, using a custom `BaseRagasLLM` subclass that delegates to
    the existing `groq_client.send_prompt` (backend/app/groq_client.py) instead
    of adding a new LLM provider dependency. On ImportError or judge-call failure,
    falls back to the current regex heuristic (kept as a private helper).
  - trulens_eval.evaluate_explainability(answer) becomes `async def`. It defines a
    minimal custom TruLens `Provider` whose scoring method also delegates to
    `groq_client.send_prompt`, wired into a real TruLens `Feedback` that scores
    explanation clarity/rationale presence — not a full `TruApp`/`TruChain`
    instrumentation of the chat flow (that would require restructuring the request
    path, which is explicitly out of scope). Same ImportError/failure fallback
    pattern as above.
  - Both functions return their existing keys unchanged, plus `*_score` (0-1 float)
    and `evaluator_engine` ('ragas'/'trulens' vs 'heuristic_fallback').
  - main.py:294-297 adds `await` to both call sites. No other call sites change;
    the code-mode heuristics (code_fairness/code_explainability) are untouched.
  - database.py gains get_eval_metrics_summary(limit), mirroring
    get_guardrail_report()'s existing query/aggregation pattern, reading
    audit_events where mode == 'framework' and parsing the responsible_ai JSON.
  - main.py gains GET /reports/evaluations, mirroring GET /reports/guardrails
    (same auth dependency: Depends(get_current_user), same limit/query-param style).
  - Frontend: api.js gains fetchEvaluationReport() (mirrors fetchGuardrailReport()).
    New EvaluationDashboard.jsx added to the admin screen next to
    GovernanceDashboard, using small hand-rolled inline-SVG charts (no new npm
    dependency, matching the frontend's current zero-UI-library convention).
    MessageBubble.jsx gets the new score fields added to its existing per-message
    display (additive, not a redesign). ResponsibleAIPanel.jsx was left unchanged
    on closer inspection: it renders the runtime `policy` config, not per-message
    `responsibleAI` data, so fairness/explainability scores don't belong there —
    the original design record's assumption about that component was incorrect.

Owning components:
  - backend/app/framework_mode/ragas_eval.py (fairness evaluator)
  - backend/app/framework_mode/trulens_eval.py (explainability evaluator)
  - backend/app/main.py (/chat framework-mode branch, new /reports/evaluations route)
  - backend/app/database.py (new aggregation query)
  - frontend/src/api.js, frontend/src/components/EvaluationDashboard.jsx,
    MessageBubble.jsx, ResponsibleAIPanel.jsx, App.jsx (mount point)

Data flow:
  /chat (framework mode) -> answer generated by Groq -> framework_fairness(answer)
  and framework_explainability(answer) each make one additional Groq call (via
  the new judge adapters) -> scores merge into ResponsibleAIResponse -> persisted
  into audit_events.responsible_ai (existing path, unchanged) -> new
  GET /reports/evaluations reads audit_events and aggregates -> frontend dashboard
  fetches and renders.

API or schema changes:
  - New route: GET /reports/evaluations (additive, no breaking change).
  - No Pydantic schema changes required — ResponsibleAIResponse.fairness/
    .explainability are already untyped dicts, so new keys pass through.

Policy and safety behavior:
  Unchanged. This work does not touch Guardrails/policy enforcement.

Privacy and retention behavior:
  Unchanged. The judge LLM calls send only the already-generated answer text (already
  passed through output privacy redaction earlier in the same request at
  main.py:264-276) to Groq — no new raw sensitive data leaves the gateway boundary.
  No new retention: scores live inside the existing audit_events retention policy.

Authentication and authorization:
  GET /reports/evaluations uses the same Depends(get_current_user) dependency as
  the existing GET /reports/guardrails — no new authz rule needed.

Observability and audit events:
  Existing tracer spans around fairness_check/explainability_check
  (main.py:294-297) are kept; no new span structure needed since the async
  await sits inside the same span context managers already there.

Failure and fallback behavior:
  Both evaluators degrade to their current heuristic behavior (never a 500) if:
  the library import fails, the Groq API key is missing, or the judge call raises.
  This mirrors the exact pattern already used in guardrails_safety.py and
  presidio_privacy.py for the same class of failure.

Compatibility impact:
  /chat's external HTTP contract is unchanged (still one synchronous request/response
  per call — this does not introduce a background/async workflow, only internal
  `await` on I/O within the same request lifecycle, consistent with the "keep
  interactive chat synchronous" design constraint). New response fields are additive.

Test strategy:
  See docs/claude-development-cycle/records/2026-09-07-evidence-record.md (produced
  in the TEST phase): focused checks (real scores present; fallback path verified by
  simulating judge failure), regression baseline (compileall + frontend build),
  and security checks (auth on the new endpoint; no new raw-data leakage).

Rollback strategy:
  Pure git revert of the feature branch; no data migration, no schema change, no
  new secret to unwind.

Human approvals:
  Requirements Record and this Design Record approved together via the plan-mode
  review by joseph.stephenr@gmail.com on 2026-09-07 (see requirements record's
  PLAN Gate note). No auth/database/infra owner sign-off is separately required
  because this change adds no new table, no new auth rule beyond reusing an
  existing dependency, and no infra module changes.
```

## EXEC-time API confirmation (2026-09-07)

Before writing production code, the actual `ragas` and `trulens` package APIs were verified in an isolated scratch venv (pip install + source introspection + a stub-LLM smoke test), rather than assumed from memory, since both libraries' APIs have changed materially across versions:

- **Ragas** (`ragas==0.4.x`): confirmed `ragas.llms.base.BaseRagasLLM` requires `generate_text` (sync), `agenerate_text` (async), `is_finished`. Only `agenerate_text` is actually exercised by the call path used here. `ragas.metrics.AspectCritic(name, definition, llm=...)` exposes `await metric.single_turn_ascore(SingleTurnSample(user_input=..., response=...))` directly — this bypasses the heavier `ragas.evaluate()`/`Dataset`/executor machinery (built for batch offline evaluation, not a single live request) and returns a plain `int` (0 or 1, since `AspectCritic`'s default output type is binary — it is an LLM yes/no rubric check, not a graded percentage). Verified end-to-end with a stub `BaseRagasLLM` returning canned JSON — the full prompt-build/parse/score round trip works. `generate_text` (sync) is required by the ABC but is never called on this path, so it raises `NotImplementedError` with a one-line note. No new dependency beyond `ragas` itself is needed for the LLM wrapper (it already pulls in `langchain_core` transitively, which supplies `Generation`/`LLMResult`).
- **TruLens** (`trulens-core` + `trulens-feedback`, both `2.14.x` — the modern modular split; the legacy `trulens-eval` package is not used): confirmed the integration point is `trulens.feedback.llm_provider.LLMProvider`, subclassed with a `model_engine` field and one overridden method, `_create_chat_completion(self, prompt=None, messages=None, response_format=None, **kwargs) -> str` (synchronous). The base class's `generate_score(system_prompt, user_prompt, min_score_val, max_score_val)` handles prompting, JSON/plain-text score parsing, and normalization to 0-1, calling our override through `self.endpoint.run_in_pace(...)` (`core_feedback.endpoint.Endpoint(name='groq')` — a plain rate-pacing/retry wrapper, no database or global TruLens session required for this direct-call usage). Because `generate_score` performs a blocking call, `trulens_eval.py`'s async wrapper runs it via `asyncio.to_thread(...)` so the FastAPI event loop is not blocked. `_create_chat_completion` is implemented with its own small synchronous `httpx` call to the same Groq chat-completions endpoint/model/key as `groq_client.py` (rather than calling the async `groq_client` directly, which isn't safe to invoke from this sync hook) — same credential, same model, no new secret. `response_format` is ignored; the system prompt instructs the model to return `{"score": <0-10>, "reason": "..."}`, which `generate_score`'s JSON-first parser consumes directly.
- Dependency footprint added: `ragas` (pulls in `langchain_core`/`langchain_openai`/`instructor` transitively, unused directly), `trulens-core`, `trulens-feedback` (pulls in `pandas`, `sqlalchemy`, `alembic`, `opentelemetry-*`, `nltk`, `scikit-learn`, `scipy`). All pure-Python wheels — no new apt packages expected in `backend/Dockerfile`. `nltk`'s sentence tokenizer is imported but never invoked by the `generate_score` path used here, so no runtime NLTK data download is triggered.
